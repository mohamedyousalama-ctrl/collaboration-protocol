every step

## 2.2 Loop Stages

**Stage 1 — Signal Capture**
- System receives user input (text, selection, gesture)
- Input is treated as a **signal**, not as intent or instruction
- No interpretation or execution occurs at this stage

**Stage 2 — Signal Classification**
- System assesses the signal for:
  - Clarity (is meaning unambiguous?)
  - Intent presence (does signal contain or imply a request for action?)
  - Context fit (does signal belong to current context?)
- Classification outcomes:
  - `clear` — Signal is unambiguous and fits context
  - `ambiguous` — Signal requires clarification
  - `out_of_scope` — Signal does not fit current context

**Stage 3 — Decision Point**

| Classification | System Response |
|----------------|-----------------|
| `clear` + no action requested | Proceed to response (no gate) |
| `clear` + action requested | Proceed to Intent Verification (Stage 4) |
| `ambiguous` | Trigger FrictionEvent → Clarification Path |
| `out_of_scope` | Trigger FrictionEvent → Scope Boundary Path |

**Stage 4 — Intent Verification**
- If an action is requested, system must verify intent before proceeding
- Verification requires explicit user confirmation
- System presents:
  - Proposed intent (declaration_text, intent_type, scope)
  - Context in which intent will operate
  - Action that will result
- User may: `confirm`, `revise`, or `abandon`
- Only upon `confirm` does intent transition to `verified`

**Stage 5 — Gate Decision**

| Condition | Gate Decision |
|-----------|---------------|
| Intent verified + within context + agent permitted | **Allow** |
| Intent verified + boundary concern or risk | **Clarify** (FrictionEvent) |
| Intent not verified OR constraint violation | **Refuse** (Block + log reason) |

**Stage 6 — Action Execution**
- If gate decision is `Allow`, action proceeds
- Action is logged with full traceability
- User is informed that action occurred

**Stage 7 — Loop Reset**
- System returns to Stage 1, awaiting next signal
- All state changes are preserved and logged

---

## 2.3 Clarification Path

Triggered when signal is `ambiguous`:

1. System generates FrictionEvent (`trigger_type: ambiguous_signal`)
2. System asks user for clarification (not leading, not inferring)
3. User responds
4. System re-enters Stage 2 with new input
5. FrictionEvent is resolved and logged

---

## 2.4 Block Path

Triggered when action cannot proceed:

1. System generates FrictionEvent (appropriate `trigger_type`)
2. System informs user why action is blocked
3. Action state set to `blocked`
4. User may: revise intent, provide missing context, or abandon
5. FrictionEvent is resolved and logged
6. If user revises, system re-enters Stage 4

## 2.5 Interaction Loop Diagram (Textual)

```
User Signal
    │
    ▼
[Signal Capture]
    │
    ▼
[Signal Classification]
    │
    ▼
┌─────────────────────────────────────┐
│ Clear, no action → Respond          │
│ Clear, action → Intent Verification │
│ Ambiguous → Clarification Path      │
│ Out of scope → Scope Boundary Path  │
└─────────────────────────────────────┘
    │
    ▼
[Intent Verification]
    │
    ▼
[Gate Decision: Allow / Clarify / Refuse]
    │
    ▼
[Action Execution] (if allowed)
    │
    ▼
[Log & Reset]
    │
    ▼
Await next signal
```

---

## 2.6 Constraints on the Loop

- System never infers intent from signal alone
- System never executes without passing through Gate Decision
- Every FrictionEvent must be logged
- Every action must reference a verified intent
- User is always informed of gate decisions and their reasons
